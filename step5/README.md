# Step 5 Test playbook (Team 9)

This is the complete procedure for every Step 5 test. A tester following it should not need to ask the team for anything. Requirements R1–R8 and the predictions are frozen in [`../STEP4.md`](../STEP4.md); nothing here may change them.

**Precondition:** the Step 4 freeze commit exists (`git log --oneline -- STEP4.md`) and is older than every file under `step5/results/`.

## 0. Roles and machines

| Role | Machine | Runs |
|---|---|---|
| Service PC | Lenovo 83JT, Intel Core Ultra 7 256V, 16 GB, Windows 11 (details: `evidence/step4/service-hardware.txt`) | Docker Compose stack (API, PostgreSQL, Ollama on CPU), `step5/service/*.ps1`, accuracy test |
| Load-generator PC | second PC (details: `evidence/step4/load-generator-hardware.txt`) | JMeter 5.6.3 only, via `step5/jmeter/run_loadgen.ps1` |

The load generator never runs on the service PC. The accuracy test is strictly sequential (one request in flight), so the client process uses negligible CPU and runs on the service PC so that its latency excludes Wi-Fi.

Both PCs: plugged into mains power, sleep disabled, no other heavy programs, same network. Setup for the second PC: [`LOADGEN_SETUP.md`](LOADGEN_SETUP.md).

## 1. Fixed test inputs

| Input | File | Content |
|---|---|---|
| Load traffic | `step5/data/tickets_load.tsv` | 840 team-9 rows 9000–9839 (all non-golden rows), JSON-escaped request bodies. Generated by `python step5/scripts/prepare_data.py` from the committed workbook. |
| Search terms | `step5/data/search_terms.csv` | 20 agent queries, used in rotation. |

Common inference settings for all candidates (`app/classifier.py`): same system prompt, `format: json`, `temperature: 0`, `num_ctx: 4096`, Ollama 0.12.3, Q4_K_M weights.

## 2. Test A Accuracy (per candidate)

1. Service PC: `.\step5\service\switch_model.ps1 -Model <tag>`. This saves logs, deploys the model, sends two synthetic warm-up tickets, empties the database and checks that `/stats` total = 0.
2. Service PC: `python step5/scripts/accuracy_test.py --label <label> --model <tag>`. This sends all 160 golden tickets in row order, one at a time, through `POST /tickets`. Request IDs are `acc-<label>-<row>`.
3. Service PC: `.\step5\service\save_logs.ps1`.
4. Output: `step5/results/<label>/accuracy/` contains `predictions.csv`, `confusion_matrix.csv`, `summary.json` and `summary.md` (overall and per-category accuracy, R7 conformance, single-request latency p50/p95/p99).

A non-201 response counts as incorrect and as an output-conformance failure. No retries.

| Label | Tag |
|---|---|
| `gemma3-1b` | `gemma3:1b-it-q4_K_M` |
| `qwen3-4b` | `qwen3:4b-instruct-2507-q4_K_M` |
| `llama3.1-8b` | `llama3.1:8b-instruct-q4_K_M` |

## 3. Test B Open-loop load test (per candidate)

Arrival rates come from `workload/WORKLOAD.md` §8 and `STEP4.md` §7:

| Level | POST /tickets per hour | GET /search per hour |
|---|---:|---:|
| `average` | 43 | 130 |
| `peak` | 81 | 243 |
| `headroom` (R1–R4 acceptance condition) | 105 | 316 |

Each run is 2 min warm-up + 20 min measurement + 1 min drain (no new arrivals), then a 60 s cooldown. Each level gets **3 runs**, with arrival seeds 1, 2 and 3. Both thread groups use `random_arrivals`, so inter-arrival times are exponential at the stated mean rate (open-loop: arrivals do not wait for responses). HTTP connect timeout is 10 s and response timeout 310 s, just above the API's 300 s Ollama timeout.

Procedure per candidate (do Test A for all candidates first, or redeploy with `switch_model.ps1` before each load batch so that the database starts empty):

1. Service PC: `.\step5\service\switch_model.ps1 -Model <tag>`, then tell the load-generator operator the label.
2. Load-generator PC:
   ```powershell
   git pull
   .\step5\jmeter\run_loadgen.ps1 -ServiceHost <service-ip> -ModelLabel <label> -Levels average,peak,headroom
   ```
   This takes about 3 h 40 min. For each run it writes `results.jtl`, `jmeter.log`, `console.log`, `run.properties`, `meta.json` and `/stats` before and after to `step5/results/<label>/<level>/run<N>/`.
3. Load-generator PC: `git add step5/results; git commit -m "Step 5 load results <label>"; git push`.
4. Service PC: `.\step5\service\save_logs.ps1` **before** switching to the next model, because recreating the API container discards its log.

Do not stop a run early or delete a run because its result looks bad. If a run is invalid for an external reason (power, network drop), keep its folder, rename it `run<N>_invalid`, write the reason in `meta.json`, and re-run it.

## 4. Test C Stress test (one candidate: `qwen3-4b`)

Purpose: find the maximum sustainable `POST /tickets` arrival rate, meaning the point where completions stop keeping up with arrivals and latency grows without bound.

1. Service PC: `.\step5\service\switch_model.ps1 -Model qwen3:4b-instruct-2507-q4_K_M`.
2. Load-generator PC:
   ```powershell
   .\step5\jmeter\run_loadgen.ps1 -ServiceHost <service-ip> -ModelLabel qwen3-4b -Stress -RampStartPerHour 60 -RampEndPerHour 1200 -RampMin 40
   ```
   POST arrivals hold at 60/h for the 2-min warm-up, then ramp linearly to 1200/h over 40 min. Searches stay at 316/h throughout.
3. Service PC: `.\step5\service\save_logs.ps1`.
4. Analysis writes `timeline.csv` (per minute: arrivals, successful completions, approximate backlog, latency). **Limit found** = the offered rate at which completions per minute stop tracking arrivals and the backlog rises monotonically. The run also shows the failure mode beyond the limit, such as 502 errors after the 300 s timeout.

## 5. Analysis and reconciliation

```powershell
git pull
python step5/scripts/analyse_jtl.py
```

This produces `step5/results/runs.csv`, `levels.csv` (mean, min, max and SD across the 3 runs), `reconciliation.csv` and `summary.md`. Every reported number comes from these files. Reconciliation checks that every JMeter sample has exactly one service-log line with the same request ID and status, and that the `/stats` increase equals the successful POSTs in that run (R4).

Metric definitions are in the docstring of `analyse_jtl.py` and are the same for every model and level.

## 7. Known factors that can make results unrepresentative

- The service PC is a laptop (Intel Lunar Lake: 4 P-cores and 4 LP E-cores, 8 threads, no Hyper-Threading). Its power and thermal behaviour can change clock speeds during long runs. It stays on mains power for all runs.
- Docker Desktop runs in a WSL2 VM limited to 8 CPUs / 7.5 GB RAM. Ollama sees only that VM.
- The PCs are connected over Wi-Fi (not Ethernet). The added latency is milliseconds, which is negligible against multi-second classification but visible in search latency.
- The Intel Arc iGPU is present but unused: Ollama runs in a Linux container without GPU passthrough, so inference is CPU-only, as in the client's deployment.
- Ticket lengths are clipped to 200–2,000 characters in the course extract (`workload/WORKLOAD.md` A8).

## 8. Observations recorded during execution

- **Same tickets in every run.** Each run reads `tickets_load.tsv` from row 9000, so runs 1–3 at a level send identical narratives. With `temperature: 0`, the success and error counts per run are therefore identical. Only the random arrival times differ, set by seeds 1–3.
- **In-flight requests are aborted at the end of a JMeter schedule.** When the Open Model Thread Group's schedule (including the drain `pause`) ends, JMeter closes the sockets of requests still waiting and records them as `Non HTTP response code: java.net.SocketException` (*Socket closed*). In the load-test runs at most one request was in flight at the end, and all nine runs per model reconcile exactly. In the Qwen3 4B stress run, 71 requests queued during the final overload minutes were cut off this way. The service log shows that the server continued processing them: 65 later failed with HTTP 502 at the 300-second Ollama timeout, and 6 completed with 201. That is why `reconciliation.csv` reports 71 status mismatches and a `/stats` delta of 234 against 233 JMeter successes for that run. The stress limit is identified well before this point (minute ~21 of the timeline), so the finding is unaffected.
- **Warm-up answers can be invalid.** `switch_model.ps1` treats an HTTP 502 on a synthetic warm-up ticket as non-fatal (the model is loaded either way). Qwen3 4B returned `bank account or service` in lowercase on the first warm-up ticket.
